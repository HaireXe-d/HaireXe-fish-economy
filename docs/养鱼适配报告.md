# 养鱼场景适配报告（QQ / B 站）

> 数据：本机 `~/.dsh/sessions/…-whale-work--/` 下的 11 个会话，1168 轮、6469 次请求、1.786B token。
> 复现：`npm run bench:whale`。

## 1. 结论

| 问题 | 答案 |
|---|---|
| 能装吗 | 能。插件不区分 QQ / B 站，两者都走同一条 DSH 会话链路（`agent/created` → assembly → 工具），不需要改养鱼插件的任何代码 |
| 默认适配吗 | **不完全**。默认 `fish.preset: work`（预唤醒 fs + shell）是按实测调的；想要"工具面归零"得显式写 `preset: chat` |
| 能省多少 | 前三刀：**2.7%–3.3%**（token 口径）/ **2.6%**（计费口径）；加上预算闸（封顶 200K）≈ **−41%**；再配 lean overlay（保留 2 万）≈ **−53%** |
| 最大的钱在哪 | 不在工具面，在这批会话**从来没触发过上下文压缩**（0 次 compaction 事件，单请求峰值 664K token）——插件的预算闸就是补这个洞 |

## 3. 两个场景的账

| 场景 | 闸门省 | 断链 | 入口裁剪复利 | 净省 | 占总量 |
|---|---|---|---|---|---|
| `chat`（工具面归零） | 31.1M | 2.2M | 29.7M | 58.7M | **3.3%** |
| `work`（fs+shell 预唤醒，推荐） | 18.4M | 0 | 29.7M | 48.1M | **2.7%**（计费 2.6%） |

`work` 的数字小一点，但它是**能真跑**的那个：0.83 次/请求的工具使用率下，
把 fs/shell 关掉会让模型反复 `tool_enable`，省下的 4.8K schema 还不够付一次往返。

## 4. 缺口：这批会话从不压缩 —— 插件现在补上了

11 个会话里 **compaction 事件数 = 0**，而单请求峰值到 664K。原因很简单：
内置压缩阈值默认 `thresholdRatio: 0.8`，要 80 万 token 才触发，这批会话刚好一直在阈值下面。

所以插件加了**预算闸**（`budget`）：每次拿到真实 usage 就记上下文体量，超过阈值就在会话空闲时调
`ctx.compaction.compactNow(agent, signal)`。养鱼预设把阈值压到 **150K**（默认 200K）。

按同一批请求做"封顶"上限估算（不含压缩本身的成本，压缩一次约烧掉被压区间的摘要费）：

| 上下文封顶 | 总量 | 相比现状 |
|---|---|---|
| 400K | 1.59B | −11% |
| 300K | 1.37B | −23% |
| **250K** | 1.23B | **−31%** |
| **200K** | 1.05B | **−41%** |
| **150K** | 0.85B | **−53%** |

注意：压缩后能保留多少由宿主后端决定（`compaction-basic` 默认 `retainRatio: 0.16` ≈ 16 万 token），
想真压到 150K 以下，得配 `extras/compaction-aggressive.yml`（`retainTokens: 20000`）一起用。
不配也能压住峰值，只是每次释放得少一些。

## 5. 推荐配置

```yaml
# ~/.dsh/profiles/web/cordis.patch.yml
- id: fish-economy
  config:
    enabled: true
    fish:
      enabled: true
      preset: work        # fs + shell 常开，其余休眠；纯聊天改 chat
    trim:
      enabled: true
      pruneToolResultChars: 2500
    budget:
      compactAtTokens: 150000   # 养鱼会话默认值；想更狠压到 100000
    gate:
      autoEnable: true    # “搜一下/看一下/记一下”会顺手唤醒 web / fs
```

配套（强烈建议，收益远大于前三刀）：

```powershell
dsh --profile web --patch "<仓库>\extras\compaction-aggressive.yml"
```

## 6. 消息路径：入站的 67.5% 是重复段

养鱼插件每条投递都捆着同一段流程说明。实测：

| 项 | 数值 |
|---|---|
| 入站消息 | 1254 条 / 0.84M 字符 |
| 其中「之前发过的段落」 | 0.57M（**67.5%**） |
| 复利到全部请求 | ≈0.19B 字符，压到 35% 后约省 **40M token（2.2%）** |

插件在 `sessionController.prompt` 外面包了一层，投递前把这些重复段换成一句「后面 N 字同上」，
第一份原样保留；异常一律按原样投递。详见 [消息路径](消息路径.md)。

## 7. 步骤数：真正的大头（5.5 步/消息）

| 指标 | 数值 |
|---|---|
| 每轮步数 | **5.5 次请求** |
| 每次请求上下文 | **272K token** |
| 压到 4 步 | 省 **27%** |
| 压到 3 步 | 省 **45%** |

插件用 `steps` 给养鱼会话加一句 60 token 的提示（"能一次做完别拆多步"），效果看 `stepsPerTurn`。
突发消息合并算过：30 秒窗口只能合并 1.5% 的轮次，却要牺牲即时性，不做。

## 8. 插件不改的三件事

1. **人设与规则**是养鱼插件自己发的用户消息（实测平均 679 字符/条，跨轮重复 4.5%），
   我们不改写它们的内容，只在同一批输入里折叠逐字重复的块。
2. **日记、日程、记忆**由养鱼插件自己维护，我们不读也不写。
3. **压缩策略**属于宿主 compaction，插件只负责"少产生"（入口裁剪），不负责"事后总结"。

## 9. 一句话

> 养鱼插件负责"像个人"，鱼缸经济学负责"少花点"。两者的接口只有一条：DSH 的会话链路。
> 所以适配成本是零，但**收益上限也不在插件本身**——想省 30% 以上，得把压缩阈值一起调了，
> 或者让每轮少拆几步。
