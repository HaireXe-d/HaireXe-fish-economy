# 效果实测

> 方法先给全，数字再说。所有数字都可以用仓库里的脚本在你自己的 `~/.dsh/sessions` 上复现。

## 1. 数据来源

| 项 | 值 |
|---|---|
| 数据 | `$DSH_HOME/sessions/**/session.v4.jsonl.zstd`（zstd 压缩的会话事件流） |
| 会话数 | 34 |
| 请求数 | 13,476 |
| 工具数 | 27（宿主默认工具面） |
| 系统提示 | 4.16K token（估算） |
| 工具定义 | 5.87K token/请求（估算，27 个 schema） |
| 总 token | 3.82B（含缓存读） |
| 缓存命中率 | 99.8% |

会话里存着**每次请求真实发出的 `request/header`**（含完整 `tools` 数组）和每条 assistant 消息的 `usage`
（`inputTokens / outputTokens / cacheReadTokens / cacheWriteTokens`），所以"工具定义吃掉多少"不需要猜。

## 2. 估算器校准

DSH 自带的估算是"4 字符 = 1 token"，对中文和 JSON 都偏低。本仓库用按码点分类的估算器：

- ASCII 可见字符：**3.7 字符/token**（散文约 4.0、JSON/代码约 3.6）
- CJK 汉字/假名/全角标点：**1 字 1 token**
- emoji 等：2 token

校准方式：拿一次真实请求的 `usage`（input + cacheRead）反推 ASCII 密度，中位数落在 3.6–3.8 之间。
命令：

```powershell
node bench/analyze-sessions.mjs --limit 40 --calibrate
```

## 3. 复现命令

```powershell
npm run bench:sessions -- --limit 40 --json bench/out/real-sessions.json
npm run bench:sim -- --json bench/out/simulate.json
```

## 5. 结果：断链代价

工具集合一变，缓存前缀就失效。模拟里按"每个会话唤醒一次分组"算：

| 项 | 数值 |
|---|---|
| 断链次数 | 34（每会话 1 次） |
| 单次代价 | ≈ 一次全价请求（均值 405K token/请求的会话里，就是 405K） |
| 34 个会话合计 | **5.3M token** |

结论：**闸门必须粘住**。如果按"每轮重新判断、反复开关"，断链代价会几十倍于省下的 schema。
这就是默认 `gate.ttlTurns: 0` 的原因。

## 6. 结果：入口裁剪（复利）

阈值 3000 字符，按"裁剪发生在第 k 次请求、后面还有 N−k 次请求"计算复利：

| 项 | 数值 |
|---|---|
| 超阈值工具结果条数 | 3,000+ |
| 一次性裁掉的字符 | ≈9.5M |
| 复利后等价 token | **80.7M** |

同一份数据里，超过 200 字的工具结果共 5,679 条、9.5M 字符——也就是说**一次性的字符量不大，
但会被后面每一次请求重发**。这是"入口裁剪"和"事后压缩"的根本区别。

## 7. 结果：重复读取值不值得做

| 项 | 数值 |
|---|---|
| 长度 ≥200 的工具结果 | 5,679 条 / 9.5M 字符 |
| 其中内容完全重复 | **47 条 / 0.3%** |

结论：**不做**。dsh-ops 的"读去重"在它自己的场景有价值，但在这批真实会话里天花板只有 0.3%，
加了反而是复杂度负担。这条结论直接决定 `src/trim.js` 里没有去重分支。

## 8. 总账

| 口径 | 现状 | 插件作用后 | 净省 |
|---|---|---|---|
| token（含缓存读） | 3.82B | 3.68B | **140.3M = 3.7%** |
| 计费（输入+输出+0.1×缓存） | 395.5M | 386.2M | **9.3M = 2.3%** |

按会话类型拆开（这才是"普通会话 vs 养鱼会话"的真实对比）：

| | 普通会话（23 个 / 7078 请求） | 养鱼会话（11 个 / 6469 请求） |
|---|---|---|
| 平均单请求 | 290K token | 276K token |
| 缓存命中 | 99.7% | 99.8% |
| 工具调用 | 1.03 次/请求 | 0.83 次/请求 |
| 工具结果（超 3000 字部分） | 6.85M（2.24M） | 3.40M（0.98M） |
| 工具面（按推荐分组常开） | 5.87K → 3.34K | 5.87K → 3.03K |
| 入口裁剪复利 | 51.0M | 29.7M |
| 闸门省 | 17.9M | 18.4M |
| **净省（token）** | **69.0M = 3.4%** | **48.1M = 2.7%** |
| **净省（计费）** | **3.2%** | **2.6%** |
| compaction 事件 | 27 次 | 0 次 |

普通会话的百分比略高，是因为它的工具结果更大（裁剪复利 51.0M vs 29.7M）；
养鱼会话的工具面省得多一点，但会话更长、历史占比更高，把百分比摊薄了。

### 预算闸：唯一能上两位数的一刀

前三刀只够 3.7%，因为 96% 的上下文是历史。插件的 `budget` 模块把上下文封顶（默认 200K，养鱼预设 150K），
按同一批请求做封顶估算：

| 上下文封顶 | 全部会话 | 普通会话 | 养鱼会话 |
|---|---|---|---|
| 400K | — | −12.6% | −11.0% |
| 300K | — | −24.6% | −23.3% |
| 250K | — | −32.8% | −31.3% |
| 200K | — | −43.0% | −40.9% |
| 150K | — | −54.8% | −52.6% |

这是上限估算（不扣压缩本身的摘要开销，也不计压缩后细节丢失带来的重读成本），
但方向明确：**把峰值从 664K 按到 200K，省的是四成，不是三个点。**

分场景看（真实会话，节选）：

| 会话类型 | 请求数 | 净省占比 |
|---|---|---|
| 长会话（>1000 请求） | 1153–2327 | 6–25% |
| 中等会话（100–500 请求） | 100–500 | 7–18% |
| 短会话（<10 请求） | 1–3 | 0%（来不及唤醒，断链也摊不平） |

## 9. 结果：消息路径（入站重复段落）

养鱼插件每条投递都捆着同一段流程说明。按 11 个养鱼会话、1254 条入站消息统计：

| 项 | 数值 |
|---|---|
| 入站消息总字符 | 0.84M |
| 其中「之前发过的段落」 | 0.57M（**67.5%**） |
| 这些段落被后续请求重复带上的总量 | 0.19B 字符 |
| 压到 35% 后可省 | ≈0.12B 字符 ≈ **40M token（2.2%）** |

计法：每条消息里重复的字符 × 该消息之后的请求数（复利），再按 3.2 字符/token 折算。

## 9.5 结果：步骤数（真正的大头）

同一批会话（1211 轮 / 6609 次请求 / 5466 次工具调用）：

| 指标 | 数值 |
|---|---|
| 每条消息平均步数 | **5.5 次请求** |
| 每次请求的上下文 | **272K token** |
| 压到 4 步 | 少 1765 次请求 ≈ **0.48B token（27%）** |
| 压到 3 步 | 少 2976 次请求 ≈ **0.81B token（45%）** |

配套的插件机制是 `steps`：给养鱼会话加一句 60 token 的提示（"能一次做完别拆多步"），
只在该会话出现。是否真的少拆步，看 `summary.json` 的 `stepsPerTurn` 有没有从 5.5 掉下来。

另外算过但**不建议做**的：突发消息合并（几秒内连发几条合成一次投递），30 秒窗口只能合并 100 轮 = **1.5%**，
却要牺牲回话即时性。

## 10. 这些数字没算进去的东西

- **上下文压缩（compaction）**：宿主自带的压缩阈值默认 0.8，压到 0.25 能让历史小一大截，
  但那不是本插件的功劳，`extras/compaction-aggressive.yml` 里给了现成 overlay。
- **提示词瘦身**：系统提示只有 4.16K，去重收益通常在 0–5% 之间，量级太小，没单列。
- **ops 减少轮次**：省的是"来回"而不是 token，无法从历史日志里反推（没有对照）。
- **感知收益**：上下文变小 → 首 token 更快、模型注意力更集中，这类收益没有量化。
- **消息路径的即时收益**：消息变短后模型读得更快，回话更利索，这部分也没量化。

## 11. 怎么在自己的机器上看

```powershell
# 1) 装好插件，正常用一阵子
# 2) 看账本
Get-Content "$env:USERPROFILE\.dsh\fish-economy\summary.json"
# 3) 或者在会话里让模型调 fish_report
```

`summary.json` 里的 `schemaBaseline / schemaAnnounced / schemaSaved / cacheHitRate / moneySaved`
就是上面几张表的实时版本。
