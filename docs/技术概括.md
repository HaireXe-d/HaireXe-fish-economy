# 技术概括

> 这份文档只讲"它为什么能省、凭什么安全、边界在哪"，所有结论都能在代码或宿主源码里对上号。
> 数字全部来自本机真实会话，复现命令见 [效果实测](效果实测.md)。

## 1. 一张图

```
                    ┌──────────────── 一次请求 ────────────────┐
                    │                                          │
  用户输入 ──▶ agent/pre-step ──▶ systemPrompt.assemble ──▶ LLM ──▶ 工具调用
                 │  (闸门预唤醒)        │   (提示词瘦身 + 记账)      │
                 │                   │                        │
                 │            sections + tools               ▼
                 │            = 4.16K + 5.87K          tools/post-execute
                 │                                       (入口裁剪)
                 │                                            │
                 └────────── tool_enable / tool_disable ◀──────┘
                                  (restrict 改名单)
```

三条杠杆分别挂在这条链的三个点上：

| 时机 | 钩子 | 动作 | 省的是 |
|---|---|---|---|
| assembly 前 | `agent/pre-step`（agent scope） | 按话术唤醒分组 | 让本该用上的工具在同一轮出现 |
| assembly 中 | `system-prompt/assemble`（waterfall） | 段去重、空白折叠、记账 | 固定前缀 |
| 工具执行后 | `tools/post-execute`（waterfall） | 超长结果掐头去尾 | 会复利的历史 |
| 任意时刻 | `tools.restrict`（agent scope） | 摘掉休眠组 | 固定前缀的大头 |

## 2. 工具闸门：为什么是 restrict，不是 deferLoading

宿主其实有一个 `deferLoading` 标记，看起来像"懒加载"，但它只影响**声明时机**：

- `deferLoading: true` 的工具不进初始声明，等下一轮 `developer/message` 的 `tool-addition` 才补；
- 路由不支持 `toolUpdate` 时（DeepSeek 是 `addition-only`），标记会被剥掉、立刻全量声明；
- 全仓库没有任何"执行期加载器"——它不解决"这一轮到底要不要带这个 schema"。

真正能把 schema 从这一轮请求里拿掉的只有 `ctx.tools.restrict({ deny })`，而且它：

- **只能在 agent scope 调**（`agent.ctx.tools.restrict`），所以天然按会话隔离；
- 只过滤"继承来的"工具（全局层 + 祖先层），本层注册的不受影响；
- 静态集合：改名单 = 撤销旧的、注册新的（我们在 `sync()` 里就是先 dispose 再 restrict）。

代价是：**名单一变，工具集合就变，缓存前缀就断**。宿主在 `toolsChanged()` 为真且路由没有 `toolUpdate`
时会重整 prompt（consolidate），那一次请求是全价。这就是为什么默认 `ttlTurns: 0`（永不回收）：
省钱的前提是"别乱动"。

## 3. 状态机

每个 agent 一份状态（`WeakMap<agent, state>`）：

```
state = {
  enabled: Set<分组>,       // 当前醒着的组
  touched: Map<组, 轮次>,   // TTL 用
  baseline: schema[],       // 第一次见到这个 agent 时的全量工具（restrict 之后就拿不到了）
  restriction: disposer,    // 当前生效的 restrict
  turns: number,
}
```

关键点：**baseline 必须在第一次 restrict 之前抓**。之后 `ctx.tools.schemas(agent)` 只会返回"还活着的"，
再想算"全量是多少"就没数据了。

`sync(agent)` 是唯一的写入口：

```
keep = META_TOOLS ∪ pins ∪ { 属于已唤醒分组的工具 }
deny = baseline - keep
dispose(旧 restriction); if (deny 非空) restriction = agent.ctx.tools.restrict({ deny })
```

## 4. 为什么入口裁剪比事后压缩划算

设第 k 次请求时裁掉 c 个字符，会话总请求数 N，则总收益 ≈ c × (N − k)。
本机数据：34 个会话、13,476 次请求，按 3000 字符阈值算，**复利后的裁剪收益 80.7M token**，
而一次性裁掉的总字符只有 9.5M 左右（差 8 倍，就是复利）。

这也是为什么 `trim` 放在 `tools/post-execute` 而不是事后扫描历史：
结果一旦进了 session，就再也不能"悄悄地"变小（要动用 surface 替换，那是 compaction 的活）。

## 5. 系统提示瘦身只做无损操作

`system-prompt/assemble` 是唯一能拿到"完整装配结果"的地方，但它也是所有插件共享的：

- waterfall 不调 `next()` 就等于否决内层，所以我们**永远先 `await next()`**，再在原地改；
- 带 `complete: true` 的段一律不碰（它代表整段提示词被接管，改它等于改别人的契约）；
- 只做三件事：逐字重复段折叠、多余空行与行尾空白、按用户配置丢弃指定段；
- `{{变量}}` 严格插值，任何"看起来像模板"的改写都可能让整轮请求抛错，所以不碰。

## 6. ops：一个工具顶六个

工具 schema 的成本按**个数**收，不按能力收。把 read/write/edit/glob/grep/stat 压成一个 `ops`：

- schema 从 6 个降到 1 个（约 −1.1K token/请求）；
- `calls` 数组一次执行多件事，省掉"读一个文件一个来回"的轮次；
- 输出本身就是紧凑格式（带行号、带省略标记），进历史时更小。

取舍：默认只读。宿主的 `read`/`write`/`edit` 走 fs 观察策略（先读后写的账本）和沙箱，
ops 绕过这些；所以 `ops.writes` 默认 false，路径默认锁在工作目录内。

## 7. 账本：三个来源，一个口径

| 来源 | 拿到什么 | 用途 |
|---|---|---|
| `system-prompt/assemble` | 本次 assembly 的 tools | 算 baseline vs announced，得到"这一轮省了多少 schema" |
| `assistant/message` 事件 | `usage.inputTokens / outputTokens / cacheReadTokens / cacheWriteTokens` | 真实用量与缓存命中率 |
| `tools/post-execute` | 裁掉的字符数 | 裁剪收益 |

报告里同时给两个口径：

- **token 口径**：用户在使用统计里看到的数字（含缓存读）；
- **计费口径**：`输入 + 输出 + 0.1 × 缓存读`（缓存读按 1/10 价折算）。

两个口径差距很大，只报 token 口径会显得省得多，只报计费口径又会显得没省——所以都报。

## 8. 失败模式与降级

| 失败 | 表现 | 我们的处理 |
|---|---|---|
| `restrict` 抛错（未知工具/权限） | 闸门失效 | 捕获 + 记 warn，降级为"只报数"，会话继续 |
| 基线读取失败 | 不知道有哪些工具 | 记空数组，之后不 restrict |
| 账本写盘失败 | 无统计 | 捕获，绝不阻塞会话 |
| 配置写错 | 插件加载失败 | 未知键 / 非法枚举在 `apply` 阶段直接抛错（不静默） |
| 会话只有 1–2 轮 | 断链代价摊不平 | 模拟里单独标出：这种会话不划算 |

## 10. 一句话总结

> 省 token 不是"把提示词改短"，而是**搞清楚哪些字节会被重复发送**，然后在它进入重复之前动手。
> 工具定义是固定开销（单请求 −82%）、工具结果是复利开销（第 k 步省下的字会再省 N−k 次）、
> 历史才是真正的天花板（占总量 96%，这也是为什么下一步要动 compaction）。
